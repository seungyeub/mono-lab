> **작성일:** 2026-08-18
> **Title:** Phase 5 — 플레이스홀더 제거 및 검색/생성형 AI 노출 최적화
> **Description:** 배포 가능 상태를 가로막는 P0 플레이스홀더(메타데이터, Contact, Work Detail, Gallery, Footer 구조, Work 데이터 정합성)를 제거하고, 전통 검색엔진(SEO)·생성형 검색엔진(GEO)·답변 엔진(AEO) 관점에서 실제 코드를 감사하여 구체적인 개선 액션을 정의한다.

## 1. 목표 (Goals)

1. **"Brand Designer" 잔재 완전 제거** — Helios 템플릿 클론 과정에서 남은 브랜드 디자이너 포지셔닝(메타데이터, Work 콘텐츠)을 실제 Frontend Engineer 포트폴리오로 전환한다.
2. **플레이스홀더 Zero** — Gallery, Contact, Work Detail(Hero/갤러리/Live Link), WorksSection 카드 6개 중 배포 전 남아있는 더미 콘텐츠·죽은 링크(`href='#'`)를 모두 제거한다.
3. **Root Layout 구조 결함 수정** — Footer가 모든 서브 라우트에 강제 노출되는 레이아웃 아키텍처 문제를 해결한다.
4. **검색 가시성 인프라 구축** — 현재 전무한 sitemap/robots/OG/JSON-LD를 코드 기반으로 신설하여 SEO·GEO·AEO 세 축에서 동시에 점수를 확보한다.
5. **Works 영역을 실제 채용 담당자가 신뢰할 수 있는 수준으로 리뉴얼** — 레퍼런스 사이트 분석 결과를 반영해 프로젝트 상세 구조와 콘텐츠 뎁스를 재설계한다.

- **P2-5. 검색 가시성 인프라 구축 (sitemap · robots · OG · JSON-LD · h1 계층)** ✅ 완료
  1절 목표 4번에 있으나 실행 항목이 없어 누락돼 있던 작업이다. `0.2.0` 배포 후 점검에서 `/sitemap.xml`·`/robots.txt`·OG 이미지가 모두 404이고 홈에 `h1`이 3개(Hero·Works·FAQ)임을 확인했다 — 검색엔진이 페이지를 발견하지 못하고, 링크 공유 시 미리보기도 뜨지 않는다. 포트폴리오는 "발견되는 것"이 목적이므로 폴리싱(P3)보다 우선순위가 높다고 판단해 P2에 둔다.

  - **프로덕션 도메인 확정** (Open Question 1 해소) — `https://seungyeub.vercel.app`. 절대 URL이 필요한 모든 곳의 단일 소스로 `src/lib/siteConfig.ts`를 신설했다. 커스텀 도메인을 붙이면 `SITE_URL` 한 줄만 바꾸면 된다.
  - `app/sitemap.ts` ✅ — `getAllProjects()`를 재사용해 상세 페이지를 동적 포함. 정적 생성 라우트와 sitemap이 같은 소스에서 나온다. `/gallery`는 `/resume`로 301되므로 제외했다.
  - `app/robots.ts` ✅ — 전체 허용 + sitemap·host 안내. 공개 포트폴리오라 disallow는 두지 않고, 생성형 검색 크롤러도 막지 않는다.
  - `metadataBase` + `alternates.canonical` ✅ — 루트와 `/work`·`/resume`·`/contact`·`/work/[slug]` 전부.
  - **Open Graph / Twitter Card** ✅ — **Open Question 5는 정적 1장으로 결정.** `next/og` 동적 생성은 라우트와 런타임 비용이 늘고, 프로젝트 상세는 이미 실제 캡쳐(`meta.image`)를 갖고 있어 그것을 쓰는 편이 낫다. 기본 이미지는 사이트 톤으로 직접 제작해 `public/images/og-default.png`(1200×630)로 두고, 재생성용 HTML 소스를 `docs/plan/og-image-source.html`에 남겼다. 상세 페이지는 카드 이미지가 **실존할 때만** 덮어쓴다 — 없는 경로를 내보내면 미리보기가 깨진 채 공유된다.

### 3-2. GEO (Generative Engine Optimization) — AI 생성 검색 최적화

- **콘텐츠와 포지셔닝의 불일치가 가장 큰 리스크다.** `src/contents/work/meltdown.mdx`를 실제로 읽어보면 "독립 게임 스튜디오를 위한 브랜드 아이덴티티", "tier-1 investors 유치" 같은 **브랜드 디자인 에이전시** 서사로 작성되어 있다(Helios 템플릿 원본 카피 그대로). ChatGPT/Perplexity 같은 생성형 검색엔진이 이 사이트를 요약하면 "브랜드 디자이너"로 인용될 가능성이 매우 높다 — 메타데이터(P0-1)뿐 아니라 **MDX 본문 자체**를 실제 프론트엔드 프로젝트(문제 정의 → 기술적 의사결정 → 구현 → 성과)로 재작성해야 GEO 효과가 있다(P1-1).
- **E-E-A-T 시그널은 이미 데이터로 존재하지만 구조화되어 있지 않다.** `ExperienceSection.tsx`의 `EXPERIENCES`(5개 회사·재직기간·직무형태)와 `ACHIEVEMENTS`(정보처리기사·OCJP, 취득일·발급기관 포함)는 시각적으로만 표현되고 있다. 이를 `Person` JSON-LD의 `worksFor`/`hasCredential`로 그대로 매핑하면 AI가 "이 사람의 경력이 몇 년인지, 어떤 회사에서 일했는지"를 정확히 추출·인용할 수 있다.
- **Skills 데이터는 이미 구조화되어 있다.** `skillsData.ts`의 `SKILL_CATEGORIES`(5개 카테고리, 44개 항목, `TOTAL_SKILL_COUNT`까지 계산됨)는 GEO 관점에서 그대로 `Person.knowsAbout` 배열로 변환 가능한 정제된 데이터다. 별도 콘텐츠 작성 없이 기존 데이터를 재사용하는 것이 핵심.
- **인용 가능한 정량적 주장(quotable statements)이 부재.** 현재 어떤 프로젝트 설명에도 "N개월 만에", "트래픽 N% 개선" 같은 구체적 수치가 없다(placeholder MDX 자체가 가상 콘텐츠이므로 당연함). P1-1 재작성 시 실제 프로젝트의 정량적 성과(있다면)를 최소 1개 이상 포함시킨다.
- **FAQ 콘텐츠는 GEO 인용에 적합한 형태로 이미 작성되어 있다.** `FAQSection.tsx`의 활성 FAQ 6개는 "주로 사용하는 기술 스택은 무엇인가요?" 같은 자연어 질문-답변 쌍이다. 현재 `FAQPage` JSON-LD가 없어 AI 검색이 이를 구조화된 답변으로 인식하지 못한다 — 추가만 하면 되는 상태.

### 3-3. AEO (Answer Engine Optimization) — 답변 엔진 최적화

- **가장 시급한 조치는 메타데이터 포지셔닝 정정(P0-1)이다.** "프론트엔드 개발자 포트폴리오", "React Next.js 포트폴리오" 같은 타겟 질의에 대해, 현재 title이 `'Brand Designer Portfolio'`인 이상 애초에 답변 후보군에 들어갈 수 없다.
- **FAQ는 자연어 질문 형식으로 이미 작성되어 있어 Voice Search·PAA(People Also Ask) 친화적이다.** 다만 아코디언 UI(`FAQSection.tsx`, `useState`로 열림/닫힘 제어)라 시각적으로는 답변이 접혀 있다 — Next.js SSR이므로 HTML에는 전체 텍스트가 포함되어 크롤러가 읽는 데는 문제없지만, `FAQPage` JSON-LD 추가로 콘텐츠를 구조화·검증해두면 AI 검색·답변 엔진이 인용하기 쉬운 형태가 된다. 다만 Featured Snippet은 사이트가 직접 지정할 수 없고, Google의 FAQ rich result는 2023년 8월부터 권위 있는 정부·헬스케어 사이트 등으로 제한되어 있어(Google Search Central 공지) "노출 보장"이 아닌 "노출 가능성 향상" 정도로 기대치를 잡아야 한다 — 실제 효과는 Search Console의 노출수·클릭수·평균 게재순위·검색어 지표로 측정한다.
- **핵심 정보(기술 스택/경력/연락처)의 구조적 추출 가능성:**
  - 기술 스택: `skillsData.ts` → 이미 카테고리별 정제됨(즉시 추출 가능).
  - 경력: `ExperienceSection.tsx`의 `EXPERIENCES` → 이미 정제됨.
  - 연락처: `contact/page.tsx`가 현재 `hello@example.com` 더미 상태(P0-2)라 **AEO 관점에서 답변 불가 상태** — 실제 값 채우는 것 자체가 AEO 개선.
- **Featured Snippet 포맷 제안:**
  - 정의형: `Person.description`에 "Next.js·React·TypeScript 기반 프론트엔드 엔지니어" 형태의 한 문장 정의를 JSON-LD와 `metadata.description`에 동일하게 반영(일관성 확보).
  - 목록형: Skills Section은 이미 카테고리 목록 구조 — `knowsAbout` 배열로 그대로 노출.
  - 테이블형: `ExperienceSection`의 경력 데이터를 `BreadcrumbList`/`Person.hasOccupation` 배열로 노출하면 "경력이 몇 년인지" 질의에 테이블형 답변 후보가 됨.

## 4. Works 영역 리뉴얼 계획

레퍼런스(`https://3d-portfolio-ruby-nine.vercel.app`)는 Vite + React(SPA, SSR 없음) + Three.js/R3F + GSAP `ScrollTrigger`/`ScrollSmoother` 기반 사이트라 페이지 소스가 완전히 클라이언트 렌더링된다. 이 때문에 정적 마크업 대신 프로덕션 JS 번들(`assets/index-*.js`)에서 실제 사용된 UI 문자열을 추출해 구조를 역산했다.

### 4-1. 확인된 구조/패턴

### 4-3. 적용 방안 (제안)

1. `ProjectMetadata`(`src/lib/mdx.ts`)에 `techStack: string[]`, `github?: string`, `liveUrl?: string` 필드 추가. `github`/`liveUrl`은 optional을 유지하되(모든 과거 프로젝트가 라이브 배포·공개 저장소를 갖는다고 보장할 수 없으므로), 값이 없는 필드의 CTA는 렌더링하지 않는 것을 계약으로 명시한다(즉 "항상 함께 노출"은 값이 존재하는 프로젝트에 한정).
2. MDX frontmatter 4개 파일(P1-1과 함께) 및 신규 작성 시 위 필드 채움.
3. `work/[slug]/page.tsx`에 "Technology Stack" 섹션(칩 형태, `SkillChips.tsx` 재사용 검토) + "Impact & Results" 섹션 추가.
4. Live Website CTA 옆에 GitHub Source Code CTA 병렬 배치 — 단 각 CTA는 `meta.liveUrl`/`meta.github` 값이 존재할 때만 렌더링하고, 값이 없으면 `href='#'` 같은 더미 링크 대신 해당 CTA 자체를 생략한다(P0-3에서 제거한 죽은 링크 재발 방지).
5. MDX 콘텐츠를 실제 프로젝트 기준으로 재작성(3-2절 GEO 분석 참고).

### 4-4. 구현 확정 사항 (2026-09-02 갱신)

4-3의 제안이 구현되면서 확정·확장된 결정들. 상세 근거는 각 커밋 메시지 참조.

- **콘텐츠**: 경력기술서 프로젝트 카드 초안(v3)을 근거로 실제 프로젝트 10건 등재, Helios 가상 프로젝트 4건 삭제. 초안에 없는 주장·수치·링크는 넣지 않고, 기여도·담당 경계·검증 방식의 한계를 원문대로 유지한다.
- **스키마 확장(4-3 제안 대비 추가)**: `summary`, `overview[]`, `features[]`, `implementation{architecture, highlights[], codeSnippet, codeCaption}`, `demonstrations[]`, `impact{metrics[], outcomes[]}`, `carouselImages[]`. frontmatter는 `normalizeProjectMetadata`로 정규화되어 누락·불완전 값이 UI에 닿지 않는다.
- **상세 페이지 디자인**: "문서를 보는 것과 차이가 없다"는 피드백에 따라 레퍼런스 레이아웃(중앙 정렬 + 카드 문법 + 터미널 코드 블록)을 이식하되, **색은 사이트 톤(백색 불투명도 위계)으로 번역**한다 — 그라데이션·컬러 액센트·아이콘 칩은 쓰지 않고 명도와 번호 타일로 위계를 표현. sticky 사이드바는 폐기. 섹션 컴포넌트는 `src/features/work/detail/`로 분리.
- **CTA**: 라벨은 `Live Demo`가 아니라 **`Visit Website`** — 등재된 liveUrl이 전부 실운영 사이트여서 데모로 읽히면 안 된다. 버튼 스타일·효과는 홈 "SEE ALL WORKS"와 동일(rounded-full + hover white + 롤링 텍스트).
- **홈 노출**: 자동 최신순이 아니라 `FEATURED_SLUGS`(`src/lib/mdx.ts`)에서 **직접 슬러그를 골라 큐레이션**한다. 배열 순서 = 노출 순서, 기본 6개. `/work` 목록과 상세는 전체 유지.
- **More Works UX(Open Question 4)**: 순차 Next Project 네비게이션(마지막→처음 순환) **과** 그리드를 모두 배치 — "전체 구성 후 축소" 방침.
- **VRT**: 상세 페이지는 macOS(CoreText)와 CI 컨테이너(FreeType)가 **동일한 웹폰트(Pretendard)를 다르게 래스터화**하며 글리프 폭 차이가 긴 한글 문단에서 누적되어 줄바꿈 수·페이지 높이가 달라진다(로컬 대비 약 15%. 당초 '시스템 폰트 대체'로 추정했으나 양쪽 모두 Pretendard가 로드됨을 실측으로 확인해 정정). baseline은 컨테이너(update-snapshots 워크플로) 기준이며, 로컬에서 work-detail 스냅샷 실패는 정상이다(`development-workflow.md` 2-1절).
- **남은 입력(자료 대기)**: 프로젝트별 코드 스니펫(`implementation.codeSnippet`), Hero 캐러셀·Demonstrations 이미지. 조건부 렌더링이라 자료 추가만으로 해당 영역이 활성화된다.

## 5. Contact 리디자인 방향

**현재 문제점:**

- `mailto:hello@example.com`, Instagram/LinkedIn/Behance `href='#'` — 4개 항목 전부 클릭 시 무효 또는 가짜 값(P0-2).
- `Footer.tsx`의 `NETWORKS`는 이미 실제 값(GitHub, Pinterest, Instagram, 네이버 블로그)으로 채워져 있는데, `contact/page.tsx`는 다른 채널(Instagram/LinkedIn/Behance)을 나열 — **같은 사이트 내에서 SNS 채널 목록이 서로 다르게 표시되는 정합성 문제**도 있음.
- Contact 페이지 자체 title(`'Contact | Portfolio'`)도 브랜드 통일성이 낮음(다른 페이지는 `'Brand Designer Portfolio'` 접미사 사용).

**개선 방향:**

1. Footer의 `NETWORKS` 배열을 Single Source of Truth로 삼아 Contact 페이지 SNS 목록을 동일하게 맞추거나, 공용 데이터 모듈(`src/data/socials.ts`)로 추출해 Header/Footer/Contact 3곳에서 공유.
2. 실제 수신 가능한 이메일 주소로 교체(Resend 기반 `ContactForm`이 이미 존재하므로 폼 자체는 정상 동작 — 상단 정적 링크만 더미 상태).
3. Contact 페이지 metadata를 P0-1의 사이트 전역 타이틀 규칙과 통일.

## 7. 검증 계획 (Verification Plan)

### Lighthouse

- 기존 `.lighthouserc.cjs`는 `url: ['http://localhost:3000/']` 한 곳만 검사하며 `categories:seo`는 `error(0.9)`로 이미 설정되어 있음. **P0 작업 완료 후** 검사 대상 URL을 `/work`, `/work/meltdown`(대표 상세 페이지), `/contact`, `/resume`(구 gallery)까지 확장.
- `categories:performance`(현재 `warn(0.7)`)는 실제 이미지(P0-3)·아이콘 최적화(P2-2) 반영 후 재측정하여 임계값 상향 여부 재검토.

### Playwright VRT

- Contact/Work Detail/Gallery→Resume 페이지 콘텐츠가 실제 값으로 바뀌므로 해당 페이지의 스냅샷을 전면 갱신 필요(`e2e/snapshot.spec.ts-snapshots`).
- Footer가 서브 라우트에서 제거되면(P0-5) 모든 서브 페이지 VRT 스냅샷의 하단 영역이 바뀌므로 함께 갱신.

### SEO/GEO/AEO 감사 도구

- **Google Search Console**: 프로덕션 도메인 확정(Open Question 1) 후 등록, `sitemap.ts` 제출.
- **Rich Results Test** (`search.google.com/test/rich-results`): `BreadcrumbList`와 (해당 시) `FAQPage`·`WebSite` 등 Google이 실제 rich result 기능으로 지원하는 타입의 검색 적격성 검증 — Lighthouse SEO 카테고리는 구조화 데이터 유효성까지는 검사하지 않으므로 별도 확인 필수. `Person`은 Google의 독립 rich result 기능 대상이 아니므로 이 도구가 아닌 아래 Schema Markup Validator로 검증한다.
- **Schema.org Validator** (`validator.schema.org`): `Person` 포함 전체 JSON-LD의 문법 오류뿐 아니라 Schema.org 타입·속성·구조가 표준에 맞는지 검증(Google rich result 적격성과는 별개의 일반 스키마 유효성 검사).
- **OG 미리보기 확인**: Slack/카카오톡/X 등에 실제 URL 공유 시 OG 이미지·title이 의도대로 렌더링되는지 수동 확인(`metadataBase` 미설정 시 상대 경로 이미지가 깨지는 문제가 실제로 발생하는지 확인하는 과정이기도 함).
