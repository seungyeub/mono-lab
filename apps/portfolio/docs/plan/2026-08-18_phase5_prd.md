## 1. 목표 (Goals)

1. **"Brand Designer" 잔재 완전 제거** — Helios 템플릿 클론 과정에서 남은 브랜드 디자이너 포지셔닝(메타데이터, Work 콘텐츠)을 실제 Frontend Engineer 포트폴리오로 전환한다.
2. **플레이스홀더 Zero** — Gallery, Contact, Work Detail(Hero/갤러리/Live Link), WorksSection 카드 6개 중 배포 전 남아있는 더미 콘텐츠·죽은 링크(`href='#'`)를 모두 제거한다.
3. **Root Layout 구조 결함 수정** — Footer가 모든 서브 라우트에 강제 노출되는 레이아웃 아키텍처 문제를 해결한다.

5. **Works 영역을 실제 채용 담당자가 신뢰할 수 있는 수준으로 리뉴얼** — 레퍼런스 사이트 분석 결과를 반영해 프로젝트 상세 구조와 콘텐츠 뎁스를 재설계한다.

### 3-2. GEO (Generative Engine Optimization) — AI 생성 검색 최적화

- **콘텐츠와 포지셔닝의 불일치가 가장 큰 리스크다.** `src/contents/work/meltdown.mdx`를 실제로 읽어보면 "독립 게임 스튜디오를 위한 브랜드 아이덴티티", "tier-1 investors 유치" 같은 **브랜드 디자인 에이전시** 서사로 작성되어 있다(Helios 템플릿 원본 카피 그대로). ChatGPT/Perplexity 같은 생성형 검색엔진이 이 사이트를 요약하면 "브랜드 디자이너"로 인용될 가능성이 매우 높다 — 메타데이터(P0-1)뿐 아니라 **MDX 본문 자체**를 실제 프론트엔드 프로젝트(문제 정의 → 기술적 의사결정 → 구현 → 성과)로 재작성해야 GEO 효과가 있다(P1-1).
- **E-E-A-T 시그널은 이미 데이터로 존재하지만 구조화되어 있지 않다.** `ExperienceSection.tsx`의 `EXPERIENCES`(5개 회사·재직기간·직무형태)와 `ACHIEVEMENTS`(정보처리기사·OCJP, 취득일·발급기관 포함)는 시각적으로만 표현되고 있다. 이를 `Person` JSON-LD의 `worksFor`/`hasCredential`로 그대로 매핑하면 AI가 "이 사람의 경력이 몇 년인지, 어떤 회사에서 일했는지"를 정확히 추출·인용할 수 있다.
- **Skills 데이터는 이미 구조화되어 있다.** `skillsData.ts`의 `SKILL_CATEGORIES`(5개 카테고리, 44개 항목, `TOTAL_SKILL_COUNT`까지 계산됨)는 GEO 관점에서 그대로 `Person.knowsAbout` 배열로 변환 가능한 정제된 데이터다. 별도 콘텐츠 작성 없이 기존 데이터를 재사용하는 것이 핵심.
- **인용 가능한 정량적 주장(quotable statements)이 부재.** 현재 어떤 프로젝트 설명에도 "N개월 만에", "트래픽 N% 개선" 같은 구체적 수치가 없다(placeholder MDX 자체가 가상 콘텐츠이므로 당연함). P1-1 재작성 시 실제 프로젝트의 정량적 성과(있다면)를 최소 1개 이상 포함시킨다.
- **FAQ 콘텐츠는 GEO 인용에 적합한 형태로 이미 작성되어 있다.** `FAQSection.tsx`의 활성 FAQ 6개는 "주로 사용하는 기술 스택은 무엇인가요?" 같은 자연어 질문-답변 쌍이다. 현재 `FAQPage` JSON-LD가 없어 AI 검색이 이를 구조화된 답변으로 인식하지 못한다 — 추가만 하면 되는 상태.

### 3-3. AEO (Answer Engine Optimization) — 답변 엔진 최적화

- **가장 시급한 조치는 메타데이터 포지셔닝 정정(P0-1)이다.** "프론트엔드 개발자 포트폴리오", "React Next.js 포트폴리오" 같은 타겟 질의에 대해, 현재 title이 `'Brand Designer Portfolio'`인 이상 애초에 답변 후보군에 들어갈 수 없다.
- **FAQ는 자연어 질문 형식으로 이미 작성되어 있어 Voice Search·PAA(People Also Ask) 친화적이다.** 다만 아코디언 UI(`FAQSection.tsx`, `useState`로 열림/닫힘 제어)라 시각적으로는 답변이 접혀 있다 — Next.js SSR이므로 HTML에는 전체 텍스트가 포함되어 크롤러가 읽는 데는 문제없지만, `FAQPage` JSON-LD 추가로 Featured Snippet 노출 가능성을 명시적으로 높일 수 있다.
- **핵심 정보(기술 스택/경력/연락처)의 구조적 추출 가능성:**
  - 기술 스택: `skillsData.ts` → 이미 카테고리별 정제됨(즉시 추출 가능).
  - 경력: `ExperienceSection.tsx`의 `EXPERIENCES` → 이미 정제됨.
  - 연락처: `contact/page.tsx`가 현재 `hello@example.com` 더미 상태(P0-2)라 **AEO 관점에서 답변 불가 상태** — 실제 값 채우는 것 자체가 AEO 개선.
- **Featured Snippet 포맷 제안:**
  - 정의형: `Person.description`에 "Next.js·React·TypeScript 기반 프론트엔드 엔지니어" 형태의 한 문장 정의를 JSON-LD와 `metadata.description`에 동일하게 반영(일관성 확보).
  - 목록형: Skills Section은 이미 카테고리 목록 구조 — `knowsAbout` 배열로 그대로 노출.
  - 테이블형: `ExperienceSection`의 경력 데이터를 `BreadcrumbList`/`Person.hasOccupation` 배열로 노출하면 "경력이 몇 년인지" 질의에 테이블형 답변 후보가 됨.

## 4. Works 영역 리뉴얼 계획

레퍼런스(`https://3d-portfolio-ruby-nine.vercel.app`)는 Vite + React(SPA, SSR 없음) + Three.js/R3F + GSAP `ScrollTrigger`/`ScrollSmoother` 기반 사이트라 페이지 소스가 완전히 클라이언트 렌더링된다. 이 때문에 정적 마크업 대신 프로덕션 JS 번들(`assets/index-*.js`)에서 실제 사용된 UI 문자열을 추출해 구조를 역산했다.

### 4-1. 확인된 구조/패턴

- **홈 프로젝트 리스트**: `project-list-wrapper overflow-hidden`, `showcase-card`, `first-project-wrapper cursor-pointer` 등 클래스명으로 미루어 카드형 쇼케이스 리스트(첫 번째 카드가 강조되는 레이아웃)로 구성.
- **프로젝트 상세 섹션 구성**: `"Project Overview"`, `"Technology Stack"`, `"Project Impact & Results"`, `"What makes this project special"` — 즉 개요 → 기술 스택 → 성과 → 차별점 순서의 4단 구조.
- **이중 CTA**: `"Live Demo"` / `"Try It Live"` + `"View Source Code"` — 라이브 링크와 GitHub 소스 링크를 항상 함께 노출(실제 GitHub URL이 프로젝트별로 하드코딩되어 있음을 번들에서 확인).
- **순차 네비게이션**: `"Next project in progress"`, `"Back to Portfolio"` — 상세 페이지 하단에 다음 프로젝트로 넘어가는 링크와 목록 복귀 링크를 함께 배치.
- **카피 톤**: `"that Deliver Result"`, `"into Real Projects"` 등 성과 지향적 문구 사용.

### 4-2. 현재 우리 Work Detail(`work/[slug]/page.tsx`)과의 격차

| 레퍼런스                                          | 현재 구현                                                                                | 격차                                                                                                                     |

## 5. Contact 리디자인 방향

**현재 문제점:**

- `mailto:hello@example.com`, Instagram/LinkedIn/Behance `href='#'` — 4개 항목 전부 클릭 시 무효 또는 가짜 값(P0-2).
- `Footer.tsx`의 `NETWORKS`는 이미 실제 값(GitHub, Pinterest, Instagram, 네이버 블로그)으로 채워져 있는데, `contact/page.tsx`는 다른 채널(Instagram/LinkedIn/Behance)을 나열 — **같은 사이트 내에서 SNS 채널 목록이 서로 다르게 표시되는 정합성 문제**도 있음.
- Contact 페이지 자체 title(`'Contact | Portfolio'`)도 브랜드 통일성이 낮음(다른 페이지는 `'Brand Designer Portfolio'` 접미사 사용).

**개선 방향:**

1. Footer의 `NETWORKS` 배열을 Single Source of Truth로 삼아 Contact 페이지 SNS 목록을 동일하게 맞추거나, 공용 데이터 모듈(`src/data/socials.ts`)로 추출해 Header/Footer/Contact 3곳에서 공유.
2. 실제 수신 가능한 이메일 주소로 교체(Resend 기반 `ContactForm`이 이미 존재하므로 폼 자체는 정상 동작 — 상단 정적 링크만 더미 상태).
3. Contact 페이지 metadata를 P0-1의 사이트 전역 타이틀 규칙과 통일.

## 6. 기술적 결정 필요 사항 (Open Questions)

1. **프로덕션 도메인 확정** — `metadataBase`, `sitemap.ts`의 절대 URL, JSON-LD `url` 필드에 필요. Vercel 기본 도메인(`*.vercel.app`)을 그대로 쓸지 커스텀 도메인을 구매할지 결정 필요.
2. **Resume 콘텐츠 형식** — Gallery→Resume 전환 시 PDF 다운로드 링크 제공 방식인지, 웹 페이지 형태(경력·기술 스택 재구성)인지 결정 필요. 후자라면 `ExperienceSection`/`skillsData.ts` 데이터를 재사용 가능.
3. **Work Detail 실제 에셋 확보 경로** — Hero 이미지·갤러리 4장·프로젝트별 실제 스크린샷을 신규 촬영/제작할지, 기존 `portfolio`(구 프로젝트) 자산을 재사용할지.
4. **More Works 영역 UX 방향** — 현재 그리드형(추천 2개)을 유지할지, 레퍼런스처럼 Next Project 순차 네비게이션으로 교체할지(4-2절).
5. **OG 이미지 생성 방식** — 정적 이미지 1장 vs `next/og`의 `ImageResponse` 기반 페이지별 동적 생성.
6. **StoryAnimation 배치 위치** — 어느 섹션/페이지에 삽입할지, 혹은 향후 재사용을 위해 보류(미배치) 상태로 둘지.

## 7. 검증 계획 (Verification Plan)

- Contact/Work Detail/Gallery→Resume 페이지 콘텐츠가 실제 값으로 바뀌므로 해당 페이지의 스냅샷을 전면 갱신 필요(`e2e/snapshot.spec.ts-snapshots`).
- Footer가 서브 라우트에서 제거되면(P0-5) 모든 서브 페이지 VRT 스냅샷의 하단 영역이 바뀌므로 함께 갱신.

### SEO/GEO/AEO 감사 도구

- **Google Search Console**: 프로덕션 도메인 확정(Open Question 1) 후 등록, `sitemap.ts` 제출.
- **Rich Results Test** (`search.google.com/test/rich-results`): `Person`, `WebSite`, `FAQPage`, `BreadcrumbList` JSON-LD 유효성 검증 — Lighthouse SEO 카테고리는 구조화 데이터 유효성까지는 검사하지 않으므로 별도 확인 필수.
